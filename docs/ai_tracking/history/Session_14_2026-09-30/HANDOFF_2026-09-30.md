## Part 2 — Permission overhaul (DONE ✅)

### The bug the owner spotted
> "when editing roles you can give access to tabs... but that's a full flaw"

Correct, and the real cause was worse than a missing decorator.

**`role_required` never read the permission matrix.** It only compared role
*names* against hardcoded lists. So editing a role in the UI changed the
**sidebar** but did **nothing** to view access — anyone logged in could type
`/agents/` directly.

**And the data itself was wrong:** the `Agent` role row had
`dispatch.agents = True`, granting agents the staff Agents area.

### Two other latent bugs found
- `User` has **no `role` field**. It is monkey-patched in `billing/apps.py`
  (`User.add_to_class("role", ...)`) and resolves via `SystemAdmin`. So
  `getattr(user, "role")` is the only way to read it.
- There was **no `StaffRole` row for `"Dispatch"` or `"Editor"`**, so the new
  decorators referenced roles that did not exist. Both were created, otherwise
  legitimate staff would have been locked out.

### What changed

**`billing/decorators.py`**
- `_role_allows(user, allowed_roles)` — extracted single role gate
- `module_required(module, subtab, extra_roles)` — **matrix-driven**; makes
  the Edit Roles screen actually enforce access
- `action_required(module, action, subtab, extra_roles)` — action-level gate,
  e.g. view agents but not create them
- Helpers `_module_allows`, `_action_allows`

**`billing/models.py`** — `StaffRole.has_action_perm()` / `get_action_perm()`.
Stored in `subtab_permissions["_actions"]`, so **NO MIGRATION NEEDED**
(`migrate --check` is clean). Shape:
```json
{"_actions": {"dispatch": {"agents": {"view": true, "create": false}}}}
```

**`billing/views/staff.py`** — `manage_roles` now preserves the `_actions` key
when it rewrites `subtab_permissions` on save. Without this, editing any role
would silently wipe the new action permissions.

**`billing/apps.py`** — the in-memory `AllPerms` / `DefaultPerms` classes now
expose `has_action_perm` / `get_action_perm`.

**Views guarded** (~50 across 7 dispatch modules + billing):
`dispatch/views.py`, `views_queue.py`, `views_approval.py`,
`views_management.py`, `pipeline_views.py`; plus `agent_list`, `view_agent`,
`add_agent`, `edit_agent`, `delete_agent`, `staff_list`, `manage_roles`.

Role lists used: `["Admin", "Editor", "Staff", "CSR", "Dispatch"]`.

### Role data corrected
- **Agent** → all modules off, `subtab_permissions = {}`. Agent Portal only.
- **Technician** → dispatch on for field work, all staff subtabs denied.
- Created missing rows: **Dispatch**, **Editor**.

> [!TIP]
> **RequestFactory gotcha (Rule 29b).** A `WSGIRequest` has no `.user`, so
> `@login_required` raises `AttributeError`. Assign `req.user` first. If the
> view you are testing uses `messages.error()` on the denial path (which is
> exactly what a *correct* block does), you must also attach
> `SessionMiddleware` + `MessageMiddleware` and a `FallbackStorage`, or you
> get `MessageFailure`. **That crash actually proves the block worked.**
